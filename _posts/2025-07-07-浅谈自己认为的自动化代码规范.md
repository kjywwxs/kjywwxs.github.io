## 前言

在管理团队用例自动化写作，以及持续看护的过程实际中，遇到了一些问题，总结出以下要求原则

> 团队的自动化用例都偏向完整业务场景，不同于代码层面的DT

## 自动化原则


从最开始**用例设计**，以及**挑选哪些用例实现自动化**的时候，需要遵循以下原则
|  原则 |  详述 |
| ------------ | ------------ |
| 功能点单一原则  | 单一功能验证：每个脚本应只验证一个功能点，避免在单个脚本中验证多个功能，这有助于定位问题和减少脚本间的耦合。  |
| 验证点明确原则  | 验证点聚焦：在脚本中只对关键的验证点进行验证，而不是对整个脚本的每一步都进行验证。这有助于减少不必要的代码量和提高测试效率。 |
| 成本效益原则 | 成本考虑：在选择自动化测试用例时，应考虑成本效益，优先选择那些频繁执行、手动测试耗时较长或容易出错的测试用例进行自动化。  |
| 清晰的前置条件  |  前置条件明确：测试用例的上下文必须有一定的顺序性，前置条件应清晰明确，以确保测试能够顺利进行。 |


在**自动化用例脚本的实现**中，需要遵循以下原则


| 原则  |  详述 |
| ------------ | ------------ |
| 完整性原则  | 完整场景：一个自动化测试脚本应包含完整业务流程，确保测试覆盖用户操作的整个流程。 |
| 独立性原则  | 脚本独立：编写的每个脚本都应是独立的，不应依赖或影响其他脚本的执行结果。这有助于并行执行测试并减少测试间的干扰。  |
| 数据还原原则  | 数据恢复：如果测试过程中对数据进行了修改（如添加、删除或更新数据），则应在测试结束后对数据进行还原，以确保测试环境的稳定性和一致性  |
| 可回归性原则  | 可重复执行：测试用例必须是可回归的，即能够在不同的时间点和环境下重复执行，以验证系统的稳定性和可靠性。  |
| 可观测性原则  | 测试失败后应能够快速定位问题，包括日志、截图、trace等信息 |
| 灵活性和可扩展性 | 灵活设计：测试用例的设计应具有灵活性和可扩展性，以便在需求变更或系统升级时能够轻松地进行修改和扩展。  |

这几个原则的要求是层层递进的

### 部分原则的详细解释

####  数据还原性

编写用例脚本时确保用例执行完后恢复原状，**数据还原未保证则有可能影响到可回归性**
> 在还没有要求到执行效率的阶段时，最需要保证的是自动化连跑的稳定性

####  可回归性

要求用例可回归，这里有两个要求

1. 同一用例在同一个环境上连续执行，结果一致。
2. 同一个用例在不同环境（环境的软件版本相同）上执行，结果一致。
